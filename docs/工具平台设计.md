# AllMyTools 工具平台设计

## 1. Purpose and scope

AllMyTools is a cross-platform desktop platform for independently developed tools. It organizes tools into three product domains:

- Learning
- Entertainment
- Tools

The desktop shell owns platform-level behavior. Each tool owns its own user interface, local state, data model, and business logic. Tools must not depend directly on one another.

The initial release contains first-party tools only. The architecture preserves a future plugin boundary, but it does not load third-party code or expose a plugin marketplace in the initial release.

## 2. Confirmed product decisions

| Area | Decision |
| --- | --- |
| Platforms | Windows and macOS are supported. Platform parity is the target; OS-only features must degrade explicitly. Linux is out of scope for the initial product. |
| Tool forms | A tool may be a local UI workflow, a web-based workflow, a script-backed workflow, or a workflow requiring mediated native capabilities. |
| Third-party plugins | Not in the initial product. A stable manifest and capability model are retained for a future plugin SDK. |
| Privileged access | File system, network, camera, and system-command access may be required and must be capability-gated. |
| Network | Network access is allowed in the initial product. Account, synchronization, and cloud data remain future capabilities. Product analytics, privacy-policy work, and third-party service dependencies are not current requirements; document them before introducing a concrete dependency. |
| Design-system viewer | The token and component viewer is a developer debugging facility, not a primary end-user feature. |
| Desktop behavior | Multi-window, system tray residency, and keyboard shortcuts are required. |
| Theme customization | Built-in light and dark themes ship first. User themes and import/export are deferred. |
| Application identity | Use a temporary application name, icon, and release identity during the architecture-validation phase. |

## 3. Technology baseline

The confirmed baseline is Tauri 2, React, TypeScript, and pnpm. Tauri provides a small cross-platform shell and a mediated native command boundary. The UI layer must be framework-light at the contracts layer so an individual tool is not coupled to the desktop shell implementation.

Electron remains an acceptable exception for a tool that demonstrably requires Node.js or Chromium APIs unavailable through Tauri. Such an exception requires a documented reason, resource impact, and cross-platform plan before adoption.

### 3.1 已落地的工程基线（D-003）

工程初始化已建立 pnpm workspace：`apps/desktop` 承载 React/Vite 前端和 `src-tauri` 原生宿主，`packages/config` 提供共享 TypeScript 基线。根级 `package.json` 只编排开发、构建、类型检查、静态检查、测试和格式化命令；产品代码不位于仓库根目录。Windows 开发者可运行 `scripts/启动开发环境.bat` 一键执行依赖检查并启动 Tauri 开发模式。

`apps/desktop/src-tauri` 是当前唯一的原生实现位置，配置了最小窗口和 `core:default` 权限，不提供文件、网络、摄像头、系统命令或其他工具能力。D-014 已在平台服务与类型契约中建立能力中介，但尚未为具体原生能力新增 Tauri 权限；工具不得绕过这一边界。

当前桌面构建使用 Tauri 2：Windows 运行时依赖系统 WebView2；macOS 使用系统 WebKit。两端都需要在 D-015 完成实际构建、签名和功能降级验证。初始化阶段生成的 `icon.ico`、`icon.icns` 与通用 PNG 图标仅作为临时应用身份资源，后续品牌确定时统一替换。

## 4. Architecture

```text
Desktop shell
  Navigation, windows, tray, shortcuts, settings, updates, notifications
  Tool registry, lifecycle, permissions, logs, storage, typed platform APIs
    Learning module
      Independent learning tools
    Entertainment module
      Independent entertainment tools
    Tools module
      Independent productivity and utility tools
  Shared design system
    Tokens, themes, components, icons, accessibility rules
```

### 4.1 Desktop shell responsibilities

The shell owns only shared platform concerns:

- app navigation, category discovery, favorites, recent tools, and search
- window creation and restoration, tray state, and shortcut registration
- tool discovery, lazy loading, lifecycle, error containment, and version compatibility
- capability checks and native-service mediation
- namespaced storage, logging, telemetry policy, and future update support
- settings, theme selection, localization policy, and the developer design-system viewer

The shell must not contain a tool's business rules or feature-specific data model.

### 4.1.1 公用 UI 颜色覆盖契约

公用 UI 颜色由 `packages/design-tokens` 的原始和语义颜色 Token 定义。桌面壳层在设置→开发者→Token 中维护按主题（`light`/`dark`）分组的十六进制覆盖值，并使用本地存储键 `shell.theme-color-overrides` 持久化；只接受 `#RRGGBB`，无效输入不得写入。壳层切换主题时先清理旧原始与语义 CSS 变量，再将当前主题覆盖写入 `document.documentElement`，公共 UI 组件和工具通过既有 `--amt-primitive-color-*`/`--amt-color-*` 变量自动同步，不得直接读取该存储键或互相导入。

恢复默认操作只清除当前主题覆盖并立即回退 `theme.css` 的内置值。`resolveThemeTokens(theme, overrides)` 为查看器和测试提供带覆盖的类型化快照；原始和语义颜色允许覆盖，间距、尺寸、动效和组件 Token 仍由设计系统控制。该能力仅使用浏览器本地存储和 CSS 自定义属性，Windows/macOS 无额外原生依赖；未来云同步须另行定义版本化冲突契约。

### 4.2 Tool boundaries

Every tool is a package with a manifest, entry point, local state, and optional declared capabilities. A tool may call typed platform services but may not import another tool's package. Cross-tool communication is opt-in and passes through a typed, versioned platform contract.

Do not use an unrestricted global event bus. Where one is justified, define event names, payloads, producer ownership, consumer ownership, and compatibility rules in the shared contract package.

Suggested source layout:

```text
根目录/
  apps/
  packages/
  modules/
  docs/
  scripts/
  tests/
  package.json
  pnpm-workspace.yaml
  AGENTS.md
apps/
  desktop/                 Desktop shell
    src/
      app/                 Application composition and routes
      features/            Shell-only features: navigation, settings, windows
      native/              Typed front-end bridge to Tauri commands
    src-tauri/             Rust native host, capabilities, packaging
packages/
  platform-contracts/      Tool manifest, APIs, events, capabilities; no UI
  platform-services/       Storage, permissions, windows, logging
  design-tokens/           Primitive, semantic, and component token definitions
  ui/                      Shared UI components, icons, and component tests
  config/                  Shared TypeScript, lint, test, and build configuration
modules/
  learning/
    <tool-id>/             One independently deployable learning tool
  entertainment/
    <tool-id>/             One independently deployable entertainment tool
  tools/
    <tool-id>/             One independently deployable utility tool
docs/
  工具平台设计.md
  用户界面设计规范.md
  开发清单.md

```

### 4.3 Directory governance

The workspace is a pnpm monorepo. Its top-level directories have fixed responsibilities and must not become generic dumping grounds.

- `apps/desktop` composes the application. It may depend on `packages/*` and load tools through `platform-contracts`, but it must not hold tool business logic.
- `modules/<category>/<tool-id>` owns one tool end to end. It may depend on public APIs from `packages/*`; it must not import another module or `apps/desktop` internals.
- `packages/` contains reusable code only. A shared package must not depend on `apps/` or `modules/`. A dependency on one specific tool is a signal that the code belongs in that tool instead.
- `apps/desktop/src-tauri` is the only location for Rust native-host implementation. UI code calls it through typed interfaces in `apps/desktop/src/native` or `packages/platform-services`.
- `tests/` contains cross-package tests only. Unit and component tests stay next to the code they verify.
- `docs/` contains decisions, specifications, checklists, and architecture records. Documents use Chinese filenames unless a tool requires a conventional filename.
- `scripts/` contains repeatable repository automation only. Scripts must have a clear name and must not be used as a substitute for application modules.

Files at the repository root are limited to workspace configuration, contributor rules, license, and high-level project metadata. Do not add feature code, temporary exports, screenshots, or ad hoc notes at the root.

Each tool package uses the same internal organization:

```text
modules/<category>/<tool-id>/
  src/
    index.ts               Tool entry and manifest export
    pages/                 Route-level views owned by this tool
    components/            Tool-specific presentational components
    features/              Tool business workflows and state
    services/              Tool-specific adapters and data access
    types/                 Tool-local types not shared by contracts
  tests/                   Tool integration tests
  package.json
  README.md                Tool scope, capabilities, and ownership
```

When creating a new directory, choose the narrowest existing ownership boundary. A new top-level directory requires an update to this document and an explicit reason in the change description.

### 4.4 Tool manifest and lifecycle

The initial manifest is bundled at build time. Its shape must remain suitable for future signed external packages.

```ts
type ToolManifest = {
  id: string
  name: string
  version: string
  category: 'learning' | 'entertainment' | 'tools'
  entry: string
  icon: string
  capabilities: readonly Capability[]
  minPlatformVersion: string
}
```

`packages/platform-contracts` 是以上清单、能力、生命周期和版本兼容规则的唯一实现与公开入口，不依赖 UI、桌面壳或任一工具模块。清单的 `id` 必须为小写字母、数字、点和连字符构成的稳定标识；`version` 与 `minPlatformVersion` 只接受稳定的 `major.minor.patch` 版本。预发布版本及版本范围尚未定义兼容策略，当前必须拒绝。

当前最小 `Capability` 枚举为 `filesystem`、`network`、`camera`、`system-command`、`clipboard` 和 `cloud-account`。工具在清单中声明能力只表示需求，不代表能力已被授予；D-014 的平台服务层负责范围、用户授权和系统可用性检查。契约校验拒绝未知或重复声明的能力。

Tool lifecycle:

```text
registered -> capability checked -> loaded -> active -> suspended -> disposed
```

契约状态值使用 `capability-checked` 表示上图中的 capability checked。允许的迁移是正常推进 `registered -> capability-checked -> loaded -> active -> suspended`、从 `suspended -> active` 恢复，以及从任何非 `disposed` 状态转为 `disposed` 释放资源；已释放工具不可恢复，且不允许跳过能力检查或加载阶段。

The shell must isolate a failed tool so that navigation and other tools remain usable. Tools should be lazy-loaded and disposed when their window or workspace closes unless their declared workflow needs background execution.

### 4.6 工具注册、懒加载与故障隔离（D-009）

`packages/platform-services` 提供不依赖 UI 的 `ToolRegistry`。桌面壳在构建期注册工具清单和动态 `load` 函数；注册时重新校验清单并拒绝重复 ID，启动时依次执行平台版本兼容检查、能力授予检查和动态加载，状态遵循 `registered -> capability-checked -> loaded -> active`。关闭工作区通过注册器转为 `disposed`，不保留工具模块实例。

注册器释放已加载模块时会调用可选的 `dispose()` 钩子（支持同步或异步实现）；释放异常不会阻止壳层离开工具工作区。桌面壳为每次异步激活分配请求序号，过期加载结果不会覆盖后续工具选择，已完成的过期会话会立即释放。

工具动态加载失败会返回结构化的 `load-failed` 结果，桌面壳将错误限制在工具工作区并保留导航、搜索和其他工具可用。工具组件另有 React 错误边界，渲染异常显示关闭操作，不把异常重新抛到平台根节点。当前已加入 Learning、Entertainment、Tools 各一个最小内置工具，分别拥有自己的入口、清单和本地状态；它们不互相导入，也不直接依赖 `apps/desktop` 内部实现。

### 4.7 学习模块最小验证工具（D-011）

`modules/learning/note-review` 作为学习域的首个验证工具，使用 `learning.note-review.draft` 独立存储草稿；存储读写封装在工具自己的 `src/storage.ts`，平台壳和其他工具不能直接读取。工具通过平台注册器动态加载，打开后进入独立工作区，关闭时会释放 `active` 会话；它复用公共 `TextField` 和 `Button`，保存成功以状态文本反馈。桌面壳的工具错误边界保证学习工具异常不会影响其他分类。

### 4.8 娱乐模块最小验证工具（D-012）

`modules/entertainment/session-picker` 作为娱乐域的首个验证工具，维护自己的候选活动和当前会话选择。选择按钮只更新工具会话内状态，用户点击“保存选择”后才写入 `entertainment.session-picker.selection`；存储封装在工具自己的 `src/storage.ts`，不会读取学习或工具域的键。工具由 `ToolRegistry` 懒加载进入独立工作区，关闭时由桌面壳释放 `active` 会话；它复用公共 `Button`，通过 `aria-pressed` 和状态文本表达当前选择及保存结果。桌面壳错误边界继续隔离娱乐工具的加载或渲染异常。

### 4.9 工具模块最小验证工具（D-013）

文本工作台已从桌面壳的 `ToolRegistry` 与工具目录下架，桌面端不再声明对其源码包的依赖，也不会动态加载或暴露其存储命名空间。模块源码为历史实现保留，不构成当前可用工具能力。

### 4.10 文本工作台正式化与通用动效（D-018）

文本工作台下架不影响 D-018 提供的共享动效能力；动效 Token、减少动效规则和设置中的动效诊断仍由设计 Token、公共 UI 组件与桌面设置页共同维护，不依赖已下架模块。

### 4.11 日历待办正式工具（D-021）

顶部“周期打卡”按钮打开独立管理界面，不嵌套在每日待办下。

周期字段由 `weekdays`（0-6，周日为 0 的数组）或 `monthDays`（1-31 的数组）表达，未填写的旧记录按开始日期推导；旧版单值字段仍可读取。

周期打卡管理界面保持干净的网格画廊：首项固定为“+ 添加打卡”卡片，其余项目各占一张独立卡片；点击加号打开新增弹窗，点击项目主体打开编辑弹窗，点击弹窗周围遮罩可关闭，完成复选框与删除操作保持独立，删除按钮位于项目卡片右下角并使用共享红色危险按钮。

当前实现已扩展为连续滚动的年历/月历层级、独立日期详情页、两态任务看板、当日笔记与独立周期打卡：年历作为上级浏览页，月份按钮进入下级月历，不使用页签切换；月历连续展示当前月份前后共 13 个月，年历连续展示当前年份前后共 5 年，两个视图均在独立滚动容器中上下浏览，月历通过顶部左侧“← 年历”回到上级；顶部左侧“今天”只重置并滚动定位日历到今天所在范围，不进入详情，周期打卡位于顶部右侧；日期格点击后进入独立日期详情页，详情页通过顶部“← 日历”返回日历。日历工具导航和功能命令统一使用带边界的共享 `Button`。全年与月历切换使用共享动效 Token 的缩放进入动画，减少动效时直接显示结果。日期选择仅更新工具会话；日期格分别统计未开始和已完成任务，并根据 `notes` 显示无文字的彩色圆点徽标及“有笔记”辅助名称，徽标固定在日期格左下角，任务状态计数固定在右下角，避免信息重叠。日期数字在格内居中；当月日期使用共享状态色和更高文字权重，非当月日期降低表面和文字对比，今天在相同状态色基础上使用更强字重、字号和边界突出。日期详情页待办看板中的普通待办项和周期同步项均可拖拽，拖入目标列即可改变状态，卡片内同时提供勾选开关；普通待办额外提供共享 `Button` 的危险删除命令，周期同步项不提供删除命令，防止删除其周期规则。在桌面 WebView 原生拖放不可用时，鼠标/指针拖拽作为兜底路径，聚焦后也可用方向键移动状态。周期同步项的拖拽和勾选会更新对应打卡完成日期。看板下方的 `TextAreaField` 提供所选日期的一条当日笔记，用户点击“保存笔记”后写入工具自有存储；保存空内容会清除该日笔记，已有笔记时可点击启用状态下的“删除笔记”按钮显式移除，并同步清除日期徽标和当前草稿。旧的进行中状态在读取时迁移为未开始。打卡管理仅显示加号卡片与项目卡片，新增和编辑均通过原生 `dialog` 弹窗完成，支持每日、每周（开始日同星期）和每月（开始日同日期）；符合周期的实例会同步出现在日历和所选日期详情页待办看板，完成状态由打卡记录驱动，非周期日不可操作。数据契约为 `{ version: 4, todos: TodoItem[], checkIns: CheckInItem[], notes: DailyNote[] }`，`CheckInItem` 包含 `frequency`、`startDate` 和完成日期，`DailyNote` 以日期、笔记内容和更新时间保存；读取兼容旧数组、版本 1 `{ items }`、版本 2 打卡记录与无笔记的版本 3 数据，并将旧打卡迁移为每日周期；损坏或不完整记录会被忽略，任务最多保留 500 项、打卡项目最多保留 100 项、日笔记最多保留 3660 条。该工具使用 `Button`、`TextField`、`TextAreaField`、`SelectField`、`StatusBadge` 与 `FloatingNotice`，仅使用浏览器原生拖放、鼠标/指针事件、方向键、复选框、表单和对话框能力，无新增原生能力或跨平台差异。

`modules/tools/calendar-todos` 是首个面向日常使用的正式工具，在模块内维护本地日期键、日历网格、待办与打卡状态；桌面壳只通过 `ToolRegistry` 注册、懒加载和隔离它。工具不读取学习、娱乐或壳层的存储数据，也不声明文件、网络、通知、摄像头、系统命令、剪贴板或云账号能力。Windows 与 macOS 均使用浏览器本地存储，无额外原生依赖或平台差异。

日历层级约束：今天在全年概览和月历中都使用日历专用强调色、加粗字号和圆形强调底；该强调态不等同于选中态，也不使用选中边框。只有用户点击的日期才使用选中态，并使用日历专用强调色内嵌边框和日期数字强调，与悬停态区分。当月日期只在全年概览中使用日历专用强调色和加粗，并为当前月份容器增加主题边界与浅层表面，月历中的其他日期不因“当月”额外着色。年历浏览顶部不重复显示当前年份和前后周期导航；年历按年份分组且年份标题居中，每个年份标题位于月份网格上方，年份分组之间使用横向分隔线；月份按钮仅显示“X月”，年历月份沿用月历的标题、星期栏和日期网格边界语言，仅以三列紧凑网格降低密度。月历连续列表使用较小日期格。日历专用强调色通过 `color.accent.calendar` 解析，浅色主题使用暖色玫红，深色主题使用冷色青色。

### 4.11.1 日视图与时间安排（D-048）

日期详情页提供独立的日视图：使用 `00:00–24:00`、15 分钟基础刻度的纵向时间轴展示带 `startTime`/`endTime` 的普通待办；没有时间的任务继续由任务看板承载。新增待办表单和时间块编辑使用本地 `HH:mm` 输入，校验结束时间晚于开始时间；时间块支持纵向拖动并按 15 分钟吸附，拖动范围限制在当天内；时间轴仅由工具模块负责布局和交互，不引入新的平台能力。日历待办存储契约升级为版本 5，读取版本 3/4 及更早数据时保留原任务并将无时间任务视为未安排。

本节之后的日历存储契约以版本 5 为准；此前段落中出现的版本 4 仅代表历史验收记录，不代表当前写入格式。

### 4.11.2 日详情左右工作区与返回位置（D-049、D-051）

日期详情采用左右工作区：左侧只展示全天时间刻度并直接承载带时间待办的时间块，右侧从上到下放置新增待办表单、状态看板和当日笔记；桌面端两栏严格使用 1:1 比例，900px 以下降级为纵向单列。日期详情的时间轴标题行仅显示当前日期和 `00:00–24:00` 范围，不重复渲染日期或“时间安排”标题。同一界面存在多个层级返回时，返回按钮在同一操作行连续排列并从左侧开始；可见文案统一使用“← 上一级名称”，不显示“返回”，但保留完整 `aria-label`；所有返回命令统一使用共享次要 `Button` 和稳定尺寸，日历工具将“← 工具台”与当前层级返回按钮合并到同一行，其他工具保持壳层工具栏最左侧返回。

返回操作的顶部留白由 `packages/design-tokens` 的组件 Token `navigation.back-top-spacing` 统一提供，当前值为 `8px`。桌面壳工具栏和工具内容区分别保留原有水平、底部内边距，仅将顶部内边距切换到该 Token，保证各返回层级的顶部间距一致且更紧凑。

带开始/结束时间的待办在左侧全天时间轴中显示，时间块按 15 分钟刻度定位并可纵向拖动调整时间；时间轴提高每个 15 分钟槽的显示高度，使时间块的顶部和高度始终与时间比例一致，同时保证短任务标题可读。时间轴块只显示待办内容文本，不提供点击编辑入口。时间编辑在右侧任务卡片内联展开开始/结束时间输入，并由卡片内的保存/取消命令完成。带时间待办同时作为普通待办出现在右侧“未开始/已完成”任务看板中，右侧不重复提供“已安排时间”模块。

返回按钮宽度随可见文案自适应，不设置固定最小宽度；年历和月历首次进入时以今天为滚动定位中心，确保默认视野围绕当天。

日详情页返回操作行下方不显示外层分隔线，左侧日期标题上方不显示分隔线；右侧待办分区之间及时间轴内部刻度仍保留必要的结构线。

### 4.5 Storage and data ownership

Each tool owns its data. Shared storage requires an explicit platform service and a documented schema owner. Tool data is namespaced by immutable tool ID, for example `tools.image-compressor.settings`.

Future synchronization must begin with versioned records, stable IDs, timestamps, tombstones for deletions, and an explicit conflict policy per data type. Do not assume last-write-wins is suitable for learning progress, editable documents, or user theme files.

平台存储写入必须经过 `packages/platform-services` 的 `writeStorage()`，将配额不足和其他写入异常转换为结构化、可恢复的结果；工具不得让 `Storage.setItem()` 异常直接穿透到 UI。当前日历待办仍使用 WebView 本地存储，并在写入失败时保留内存中的旧数据、显示可恢复错误；当数据规模或备份需求超过本地存储能力时，应迁移到带事务的 IndexedDB/SQLite 服务，并先定义导出与恢复契约。

## 5. Capability and security model

Capabilities are declared in a manifest and granted by the shell. A tool never receives broad native access simply because it runs inside the application.

| Capability | Minimum control |
| --- | --- |
| File system | User-selected paths or scoped app directories; no unrestricted disk scanning. |
| Network | Allowlisted or user-visible destinations where practical; timeouts and offline errors required. |
| Camera | Explicit user consent and visible active-use state. |
| System commands | Typed, allowlisted commands; no arbitrary shell string execution. |
| Clipboard | Read/write only for the active user action unless a background exception is documented. |
| Cloud account | Token storage through OS credential facilities and explicit data-scope disclosure. |

Future third-party plugins require signed packages, version validation, an isolated execution context, permission prompts, revocation, and crash containment. These are prerequisites, not optional polish.

### 5.1 能力中介（D-014）

`packages/platform-services` 的 `CapabilityBroker` 是工具调用受限能力的唯一共享执行边界。每次调用按照“清单声明、系统可用、用户同意、执行操作”的固定顺序处理；未声明能力、用户拒绝、用户取消、系统不可用和操作异常分别返回可判别的结构化结果，且不会执行受保护操作。授权按不可变工具 ID 和能力名称存储，可以撤销；取消不保存为授权决定，以便用户下次主动操作时重新选择。

该中介目前只提供框架无关的类型化机制，并未在 Tauri 能力清单中增加文件、网络、摄像头或系统命令权限，也不向工具暴露裸 `invoke`。首个需要这些能力的工具必须通过 `CapabilityBroker.execute()` 提供本工具的清单、面向用户的授权请求和具体受限操作，并在修改前同步记录数据范围、权限说明及失败处理。

跨平台约束如下：文件访问仅接受用户选取的路径或应用作用域目录；网络必须定义目标、超时和离线反馈；摄像头必须有每次使用时的可见状态；系统命令必须映射到类型化白名单，不能接受任意 shell 字符串。Windows 和 macOS 上的原生实现由 `apps/desktop/src-tauri` 承载；当前没有授权实现或系统适配时，中介返回 `system-unavailable`，不得静默降级为浏览器或系统直接访问。

## 6. Multi-window, tray, and shortcuts

The shell owns all window and shortcut behavior. Tools request window operations through a platform API rather than directly creating native windows.

- Restore the primary window and relevant workspace on startup.
- The tray provides show/hide, quit, and a concise status surface. It must not become a second navigation model.
- Shortcuts have a central registry, conflict detection, user configuration, and OS-specific availability reporting.
- A tool-specific shortcut is active only when its scope is valid. Global shortcuts require explicit user opt-in.

### 6.1 多窗口、托盘与快捷键基础能力（D-008）

`apps/desktop/src-tauri` 通过官方 `tauri-plugin-window-state` 保存并恢复主窗口的位置、尺寸和最大化状态。关闭主窗口会隐藏窗口并保留托盘驻留；托盘左键可切换窗口显示，菜单提供显示主窗口、隐藏主窗口和退出 AllMyTools 三个操作。退出菜单是显式结束应用的唯一入口，避免关闭窗口误退出后台任务。

全局快捷键由 `tauri-plugin-global-shortcut` 提供，前端仅经 `apps/desktop/src/native/globalShortcut.ts` 这个受限入口注册或注销 `CommandOrControl+Shift+Space`。用户必须在设置中勾选后才会注册；注册冲突会显示可恢复提示，Web 预览和不支持的宿主会显示不可用状态，不会静默失败。快捷键偏好存储在壳层本地存储，重启后会尝试恢复，失败则自动关闭该偏好。

桌面壳同时在 `shell.workspace-state` 命名空间保存主题、当前主视图、工具分类和搜索条件，并在启动时校验后恢复这些工作区状态。正在运行的工具会话不跨重启恢复，避免重新创建未经能力检查或已失效的工具实例；应用启动后仍从主目录重新进入工具。

桌面壳的布局契约以稳定窗口为基础：最小窗口尺寸为 960×640；左侧分类导航和页面工具栏固定在壳层，主工作区填充全部剩余宽度并独立滚动；设置按钮位于主题切换右侧，不进入左侧分类页签，点击后以随视口宽高同比适配、占用大部分可用工作区的宽屏模态弹窗呈现设置，弹窗内容区独立滚动并保留稳定内边距；只有工具表单正文使用 880px 的局部可读宽度，不能用居中最大宽度限制整个工作区。窗口变窄时在 900px 以下进入降级布局，但不改变桌面端的信息架构。

这两个插件均支持 Windows 和 macOS。Windows 托盘支持左键切换；macOS 使用系统菜单栏实现同一显示、隐藏、退出菜单。窗口状态和快捷键未在 Linux 作为首发支持范围内验证，因此 D-015 前不得把 Linux 视为发布目标。

## 7. Design system and themes

The design system is specified in `docs/用户界面设计规范.md`. Components use semantic tokens only. A theme changes semantic values; it does not require component rewrites.

The initial themes are light and dark and use a neutral grayscale foundation. All interactive controls, including theme selection, use black, white, and gray semantic tokens in both themes. Information, success, warning, and danger states use vivid cyan, green, orange, and pink-red semantic colors to provide dopamine accents while preserving clarity and accessibility; destructive commands use the shared red danger button variant backed by the error semantic token, always paired with explicit text and a visible button boundary.

Settings includes a developer-facing design-system viewer that shows resolved token values, component states, and the active theme. It is read-only in the initial release.

Token 查看器每行同时展示层级、名称、中文用途说明、当前解析值和复制操作；说明直接按 Token 名称与来源类别生成，语义 Token 提供逐项用途，原始与组件 Token 提供对应色阶、间距、尺寸、动效或组件参数说明。

设置工作区按功能提供 `外观`、`快捷键` 和 `开发者` 三个页签。工作区内容从顶部按标题、页签和面板依次向下排列，不在空余高度中垂直居中。页签使用原生 `tablist`/`tab`/`tabpanel` 语义，每个页签只挂载自己的设置内容；左右方向键、上下方向键以及 `Home`/`End` 可在页签间移动，当前页签通过 `aria-selected` 和可见焦点暴露。壳层把当前页签作为 `shell.workspace-state.settingsTab` 持久化，兼容没有该字段的旧状态并默认进入“外观”；页签切换不改变工具分类、工具会话或其他模块状态。

界面标题遵循单一层级原则：当壳层顶部或页签已经提供当前页面主标题时，内容区不再重复渲染同义标题、装饰性 eyebrow 或非必要说明段落；工具内仅保留能提供独立上下文的区域标题，并通过 `aria-labelledby` 或 `aria-label` 保持区域可访问名称。该规则适用于设置、设计系统查看器和日历待办等所有工具界面。

工具台与工具专注工作区同样由壳层顶部标题承担页面识别：目录不重复显示“全部工具/搜索结果”类顶层标题，学习、娱乐和日历工具不重复显示“工具工作区”标题或介绍文案；常用/其他工具、月份、任务列等独立内容分区仍保留必要标题。

日历待办工具采用“年历 -> 月历 -> 日期详情”的页面层级：年历只承载年份和月份浏览，月份按钮进入月历，月历通过顶部返回按钮回到年历，日期点击进入详情；页面之间不做左右并排，详情通过顶部返回按钮回到日历浏览。

“开发者”页签内部继续按诊断目标拆分为 `Token`、`主题对比`、`组件状态`、`动效` 和 `UI规范` 五个子页签。`Token` 负责 Token 筛选、解析值表格和复制，`主题对比` 只展示浅色/深色语义差异，`组件状态` 同时展示公共组件目录、真实交互展厅和基础状态矩阵，`动效` 展示共享时长、缓动、120ms/180ms 的比例时间轴、当前系统减少动效状态以及一次性从 0 到 100 的组件反馈预览，`UI规范` 展示与 `docs/用户界面设计规范.md` 同步的 Token、布局、可访问性和状态规则；子页签同样提供键盘导航并使用独立的 `developer-tab-*`/`developer-panel-*` ARIA 关联，不把开发者诊断状态写入工具或模块存储空间。

### 7.3 开发者设计系统查看器（D-010）

设置页开发者区域的设计系统查看器直接读取 `packages/design-tokens` 的 `resolveThemeTokens()` 结果和 `packages/ui` 的 `uiComponentCatalog`/`uiGuidelineGroups`，并通过 `Token`、`主题对比`、`组件状态`、`动效`、`UI规范` 子页签分离诊断任务。Token 子页签展示原始、语义和组件三层 Token 的当前解析值，支持按层级、名称和值筛选以及复制名称和值；主题对比子页签展示浅色/深色语义差异；组件状态子页签展示 `packages/ui` 的二十个公共组件目录、契约、Tabs/ChoiceGroup/ToggleField/SettingRow/EmptyState/SelectField/StepperField/Disclosure/ToggleButton 的真实组合示例、StatusBadge/ProgressBar 状态反馈，以及 Button/ToggleButton/TextField/TextAreaField/InlineMessage/IconButton/NavigationItem 状态预览；动效子页签读取时长与标准缓动 Token，按真实时长比例绘制时间轴，并在不修改系统偏好的前提下展示 `prefers-reduced-motion` 状态和由五段 `180ms` 组成的可重复消息/进度反馈演示；该演示仅放大诊断体验，不影响产品交互时长；UI规范子页签展示与规范文档同步的 Token、布局导航、可访问性和状态响应式规则。

查看器不会写回 Token 源，也不维护与 Token 包分离的静态副本；颜色编辑只写入壳层的用户覆盖存储。它只属于设置工作区，不改变普通用户工具导航和工具业务边界。

### 7.1 Token 包落地（D-005）

`packages/design-tokens` 是实际 Token 的唯一来源，公开原始 Token、浅色/深色语义 Token、组件 Token 和 `theme.css`。桌面启动页通过 `data-theme="light|dark"` 选择主题，内置主题只覆写语义变量；用户颜色覆盖可通过壳层契约写入原始或语义变量，组件样式不得直接依赖原始色阶。它同时定义页面标题、工具标题、分区标题、正文、辅助文字和数据文字的字号/行高/字重层级，以及 120ms/180ms 的共享动效时长和标准缓动曲线；`prefers-reduced-motion: reduce` 时将时长归零。Token 包不依赖桌面壳或工具模块，开发者查看器应直接读取其解析结果。

### 7.4 工具台首屏排版样片（D-047）

桌面工具台首屏使用共享排版 Token 表达页面、分区、工具卡和辅助信息的层级；搜索区占满目录可用宽度，在输入框内部使用共享图标前缀，常用工具与其他工具均使用统一的可扩展网格，保持稳定卡片尺寸并支持未来增加更多工具。该样片只调整壳层排版和目录密度，不改变工具注册、存储与业务边界，后续工具身份和动效在此基础上继续演进。

### 7.2 公用 UI 组件库（D-006）

`packages/ui` 提供跨工具复用的 React 基础和复合组件与样式入口：`Button`、`ToggleButton`、`IconButton`、`NavigationItem`、`TextField`、`TextAreaField`、`EmptyState`、`InlineMessage`、受控 `Tabs`、`HorizontalTabs`、`VerticalTabs`、`ChoiceGroup`、`ToggleField`、`SettingRow`、`SelectField`、`StepperField`、`StatusBadge`、`ProgressBar` 和 `Disclosure`；其中 `Button` 统一提供主、次、危险红色三种带边界变体，供工具在共享契约内表达普通与破坏性命令，`ToggleButton` 表达独立二态状态并输出 `aria-pressed`；`HorizontalTabs` 与 `VerticalTabs` 提供不带面板的横向/竖向页签选择语义，页签项支持图标和标签组合，`ChoiceGroup` 仅兼容旧调用；同时通过 `uiComponentCatalog` 和 `uiGuidelineGroups` 提供设置查看器使用的组件契约与规范摘要元数据。桌面壳消费同一套设计 Token 的窗口和工作区尺寸，不在应用层重新定义尺寸常量。它只以 React 为 peer dependency，并消费 `packages/design-tokens` 的 CSS 变量；不依赖桌面壳、Tauri 或任何工具模块，因此 Learning、Entertainment 与 Tools 可通过公共入口独立使用。

`NavigationItem` 用于桌面壳和未来工具工作区的主导航项，工具不得重新实现图标、标签、当前页面语义或导航焦点样式。

组件库负责自身的可访问性契约：按钮在加载时禁用并公开 `aria-busy`，单行和多行文本输入通过 `label`、`aria-describedby` 和 `aria-invalid` 关联说明与错误，错误信息使用 `alert`，一般信息使用 `status`；`Tabs` 统一输出 `tablist`/`tab`/`tabpanel` 语义及 ARIA 关联，处理方向键、`Home`/`End` 导航和面板 `hidden` 状态；`ChoiceGroup` 通过 `aria-pressed` 暴露选中项，`ToggleField` 保留原生 checkbox、label 和描述关联，`SettingRow` 只负责说明与控件布局。共享组件的交互反馈、面板内容和原位消息使用 Token 的动效时长与标准缓动，减少动效时停止旋转和内容进入动画。页面业务逻辑只决定何时传入状态和文案，不得复制组件内部样式或状态语义。

## 8. Quality gates

### 8.2 Windows/macOS 质量、打包与发布基础（D-015）

Windows release 应用通过 `pnpm --filter @allmytools/desktop tauri build --no-bundle` 构建，产物为 `apps/desktop/src-tauri/target/release/allmytools-desktop.exe`。使用中的调试应用会锁定同名 `target/debug` 文件，因此调试包构建必须先关闭该实例；release 输出目录独立，不受此限制。完整 MSI 打包依赖 WiX 工具集；当前构建宿主从 GitHub 下载该工具集时超时，`winget` 安装 WiX 又要求管理员权限启用 .NET Framework 3.5，离线载荷下载同样超时，不能将未生成安装包视为发布成功。

根命令 `pnpm release:check`（实现位于 `scripts/发布环境检查.mjs`）会检查 Node.js、pnpm、Cargo、当前 Rust 目标、Tauri 配置、release 应用产物、Windows WiX/签名工具和 macOS 签名工具。它将缺少另一平台工具链或发布签名条件报告为警告，将无法构建当前平台应用的硬前置报告为失败；脚本不下载工具、不修改源码，也不把跨平台未验证结果伪装成通过。

当前开发环境仅安装 `x86_64-pc-windows-msvc` 目标，不能验证 macOS `.app`、DMG 或签名公证。发布前必须在 macOS 13 或更高版本的构建宿主完成 Apple 签名和公证，并在 Windows 构建宿主配置代码签名证书与 WiX 后生成、安装和卸载 MSI。两个平台都要验证窗口、托盘、全局快捷键与能力中介的降级反馈；当前无文件、网络、摄像头或系统命令原生授权实现，因此这些能力在两端均返回系统不可用，不存在平台间行为差异。

当前交付状态：D-015、D-016、D-017 按用户决定暂时暂停。D-015 保留已完成的 Windows release 构建和发布预检，恢复后继续处理 WiX/MSI、签名及 macOS 验证；D-016 与 D-017 尚未开始实现，恢复前仍需完成各自的前置设计决策。

### 8.1 桌面应用壳与根目录启动入口（D-007）

`apps/desktop/src/app` 当前只拥有壳层目录数据、分类导航、搜索、收藏、最近使用和设置主题状态，不导入或实现任何真实工具业务逻辑。工具台左侧将全部工具、学习、娱乐和工具统一建模为受控 `VerticalTabs`，直接复用公共页签的外框、选中态、焦点态和键盘交互，不在壳层覆盖为 `NavigationItem` 样式；设置从左侧页签移除，位于主题切换右侧并通过模态弹窗呈现。页签切换负责更新主视图或工具分类，图标只作为页签项的视觉辅助并保留文字可访问名称。工具目录使用平台契约中的 `ToolCategory` 类型：全部工具页将最近使用和收藏合并为不重复的“常用”工具块，并在后续目录中排除这些条目；分类页与搜索结果只呈现当前范围内的工具块。工具激活后壳层切换到专注工作区，不渲染左侧分类导航，工具可使用完整窗口宽度；受限工具栏提供工具名、主题、设置和返回目录命令。返回命令调用 `ToolRegistry.dispose()` 释放会话，再恢复已持久化的目录上下文。真实工具注册、入口加载、生命周期和故障隔离仍由 D-009 负责。

仓库根目录的 `启动AllMyTools.bat` 是用户明确要求的 Windows 开发启动入口例外，不属于产品代码，也不改变根目录治理规则。脚本使用 `%~dp0` 定位仓库，优先使用 `pnpm.cmd`，缺失时通过 `npm.cmd exec` 启动固定版本的 pnpm；它会按锁文件安装依赖，并以严格端口 `1420` 启动 Tauri 开发模式。端口冲突和依赖失败会给出可操作提示。原有 `scripts/启动开发环境.bat` 继续作为脚本目录内的转发入口保留。

为兼容 Windows 上 Node.js 22.12 等仍未满足 pnpm 11 最低版本要求的环境，工作区固定使用 `pnpm@9.15.5`。当系统没有独立 `pnpm.cmd` 时，根目录 BAT 通过 `npm exec` 临时调用该版本，不依赖 Corepack 的签名密钥或管理员权限；这会产生一次网络下载，后续由 npm 缓存复用。

根目录启动脚本除检查根级 `node_modules` 外，还验证桌面壳对工作区工具包的实际链接（当前包含 `apps/desktop/node_modules/@allmytools/tools-calendar-todos/package.json`）。当目录存在但工作区包未链接时，脚本会按锁文件重新执行 `pnpm install --frozen-lockfile`，避免新增工具后直接启动出现 `Failed to resolve import`；该检查不改变工具的模块边界或能力授权。

- Contract changes require type checks and compatibility review.
- Shared UI changes require light and dark visual checks plus keyboard and focus-state coverage.
- Capability changes require permission-denied, cancellation, and OS-unavailable behavior tests.
- Every tool must render loading, empty, error, and offline states where applicable.
- OS-specific features must expose a clear fallback instead of silently failing.

## 9. Delivery sequence

1. Create the desktop shell, platform contracts, category navigation, and window/tray/shortcut foundations.
2. Build the token package, light and dark themes, shared components, and developer design-system viewer.
3. Add one minimal architecture-validation tool per category. These tools may be empty-shell workflows, but each must validate registration, navigation, independent storage, lifecycle, error isolation, and shared UI reuse.
4. Add capability mediation for the first real native workflow.
5. Add account and synchronization contracts only when a concrete synced data type exists.
6. Design and validate signed plugin loading only when third-party extensibility becomes a product requirement.

### 4.12 工具调试模式（D-045）

桌面壳在工具主机和工具专注工作区提供平台级调试覆盖层。顶部主题切换旁的“调试”按钮可直接开关，使用公共 `ToggleButton` 的 `pressed`/`aria-pressed`、独立状态圆点和选中样式同步反映当前调试状态；主题浅色/深色互斥选择使用公共 `HorizontalTabs`，一次性设置、打开、返回等命令继续使用公共 `Button`。调试模式快捷键默认使用跨平台表示 `CommandOrControl+Alt+0`（Windows 为 `Ctrl+Alt+0`，macOS 为 `Command+Option+0`），用户可在设置→快捷键中通过聚焦录入修改并启用/停用；Tauri 宿主使用 `global-shortcut` 注册，浏览器宿主使用同一键盘事件契约回退。进入调试模式不弹出提示，按 `Escape` 退出调试模式。

覆盖层只观察当前工具主机或工作区，不读取工具业务状态，也不改变工具存储。它通过捕获指针移动测量元素 `getBoundingClientRect()`，按 `data-debug-kind` 或 HTML 元素类型显示区域、控件、文本的语义颜色框；点击会阻止原控件动作并打开浮动源码面板。主界面导航、工具栏、目录和设置弹窗与各工具根区域一样通过 `data-debug-target`、`data-debug-label`、`data-debug-source`、`data-debug-code` 声明源码定位和片段，未声明的后代元素仍显示 DOM 片段并明确提示缺少定位。工具主机每个界面底部均提供紧凑的临时运行输出台，记录宿主回退/全局注册、按键匹配、调试切换、悬浮、点击和退出事件，最多保留 100 条且可清空；输出台不参与调试元素捕获。调试切换事件使用约定的 `allmytools:debug-toggle` 事件名，不形成无契约的跨工具事件总线。源码元数据属于各工具自身入口，壳层只消费通用属性，不跨边界导入工具代码。

该能力仅使用浏览器 DOM、CSS Token 和现有 Tauri 全局快捷键插件；Windows/macOS 无新增原生权限，宿主不支持全局快捷键时仍可在窗口内使用键盘回退。快捷键成功切换和冲突均通过工具工作区或设置中的文字反馈呈现，不能阻塞工具或桌面壳。

源码定位补充（D-053）：解析 `data-debug-*` 时优先使用最近元素上的 `data-debug-source` 与 `data-debug-code`，格式为 `路径:行`，叶子输入、按钮或文本节点可覆盖父级区域定位，从而精确到单行源码；没有叶子声明时才回退到最近的 `data-debug-target`。
